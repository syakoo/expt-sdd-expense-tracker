# Brief: expense-claim-workflow

## Problem
作業者は立て替えた経費を精算してもらうため、領収書をまとめて承認者に申請したい。承認者は申請内容を確認し、承認するか修正を求めて差し戻したい。この流れが仕組み化されていないと、申請の状態が不明確になり、精算漏れや二重処理が起きる。

## Current State
app-foundation（ユーザー／ロール）と receipt-management（領収書）が存在する前提。申請・承認の仕組みは存在しない。

## Desired Outcome
- 作業者が自分の領収書を複数選んで申請を作成し、承認者を指定して提出できる
- 指定された承認者だけが、その申請を承認または差し戻しできる（差し戻し時はコメントを付けられる）
- 差し戻された申請は作業者が修正（領収書の追加・除外、内容修正）して再申請できる
- 承認された申請は「精算完了」となり、以後変更できない
- 申請中・承認済の申請に含まれる領収書は編集・削除できない
- 作業者は自分の申請一覧と状態を、承認者は自分宛ての申請一覧を確認できる

## Approach
申請（1 申請 = 複数領収書）を集約とし、状態遷移（下書き → 申請中 → 差し戻し → 申請中 … → 承認済）をこの spec のドメインモデル一箇所に閉じ込める。許可されない遷移や権限外の操作はドメイン層で拒否する。承認者は提出時に作業者が承認者ロールのユーザーから指定し、自分自身は指定できない。

## Scope
- **In**: 申請モデルと状態遷移、領収書の申請への紐付け、承認者の指定、承認・差し戻し（コメント）、再申請、申請一覧（作業者用・承認者用）、申請詳細、領収書ロック判定の公開、操作履歴（誰がいつどの遷移を行ったか）
- **Out**: 多段階承認、承認者の代理・自動割当、支払処理、通知

## Boundary Candidates
- 申請の状態遷移ルール（ドメインの核）
- 申請と領収書の紐付け、領収書ロック判定
- 作業者向け申請 UI／承認者向け承認 UI

## Out of Boundary
- 領収書そのものの入力・検証（receipt-management）
- ユーザー／ロールの管理と切替（app-foundation）

## Upstream / Downstream
- **Upstream**: app-foundation（現在ユーザー、承認者ロールのユーザー一覧）、receipt-management（領収書の参照）
- **Downstream**: 将来の多段階承認・通知・支払連携

## Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: receipt-management（領収書ロックのルール境界）

## Constraints
- 状態遷移の判断を UI や他 spec に漏らさない
- 1 つの領収書は同時に 1 つの申請にしか含められない
