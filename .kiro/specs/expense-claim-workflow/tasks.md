# Implementation Plan

> 前提：receipt-management の実装が完了していること（`drizzle/0001_receipts.sql`、`@/receipts/api.server`、`@/receipts/test-fixtures.server`、`@/receipts/ui` の書式）と、app-foundation が `src/start.ts` に登録している CSRF ミドルウェア。本 spec のタスクは `src/start.ts` を変更せず、変更系の Server Function の CSRF 対策はこのミドルウェアに依存する。

- [ ] 1. 基盤：前提の確認、型、テーブル、import 境界、ルートの骨組み
- [ ] 1.1 申請の型・状態と履歴のラベル・ロールの判定
  - 着手前に、receipt-management の下流向けの公開面（領収書の参照・所有者ごとの一覧・ロックの付与と解除）、テスト専用の領収書のフィクスチャ（作成・変更・削除）、外部キー参照用の領収書テーブル、表示の書式、領収書のマイグレーションが存在し、`npm run test` が成功することを確かめる。欠けていれば本 spec の作業を止めて報告する
  - ブランド型の申請 ID、4 つの状態（下書き・申請中・差し戻し・精算完了）と 5 つの履歴の種類（作成・提出・再提出・差し戻し・承認）とそれぞれの日本語ラベル、表示用のユーザー、一覧・詳細・フォーム・提出の選択肢の表示用の型、許される操作の一覧、項目ごとのエラー、各操作の結果（判別共用体）を design の ClaimTypes どおりに定義する
  - 作業者ロールなら「申請を作成できる」、承認者ロールなら「申請を確認できる」と判定する 2 つの関数を作る
  - 単体テストで、作業者のみ・承認者のみ・両方のロールのユーザーに対する 2 つの判定と、状態が 4 つこの順で並び、ラベルが「下書き」「申請中」「差し戻し」「精算完了」であることが `npm run test` で通る
  - _Requirements: 6.1, 11.1, 11.2, 12.1_

- [ ] 1.2 申請・紐付け・操作履歴のテーブル定義とマイグレーション

  - receipt-management のマイグレーションの後に `npm run db:generate -- --name claims` で生成した SQL マイグレーションとメタ情報をコミット対象に加える
  - `npm run db:setup` を既存の開発用 DB に実行すると成功し、`createTestDatabase()` で得た DB に 3 つのテーブルが空の状態で存在する
  - _Requirements: 1.5, 2.2, 2.5, 6.1, 10.3_

- [ ] 1.3 申請モジュールの import 境界

- [ ] 2.2 (P) 申請の状態遷移の規則

  - 操作者の判定には 1.1 のロールの判定を使い、申請者は作業者ロール、承認者は承認者ロールを持つことも条件にする
  - 単体テストで、4 状態 × 5 操作 × 操作者の種類（申請者・指定承認者・それ以外・ロールを失った申請者）の全組合せで、許される 7 行だけが成功し効果が表どおりであること、精算完了への操作がすべて成功しないこと、許される操作の一覧が判断と一致することが `npm run test` で通る

- [ ] 2.4 (P) 申請・紐付け・操作履歴の読み書き

  - 申請の挿入・申請者を変えない更新・削除、紐付けの置き換え（外した分を消し足した分を入れる）、履歴の追記を作る。履歴の更新・削除の関数は作らない。書き込みは自分でトランザクションを開始しない

- [ ] 2.5 申請の参照の判断（一覧・詳細・フォーム）

  - 作成・修正のフォームのデータ（作業者ロールでなければ「権限なし」、修正は申請者本人でなければ「見つからない」、修正が許されない状態なら「修正できない」、候補は他の申請に含まれていない自分の領収書とその申請の領収書）を作る
  - 結合テスト（領収書は 2.4 と同じフィクスチャで用意・変更する）で、合計金額と件数、領収書の内容をフィクスチャで変えた後に詳細と一覧の金額が変わること、指定承認者が他人の領収書の内容を受け取れること、指定外の承認者・他の作業者・存在しない ID が同じ「見つからない」になること、下書きが申請者以外に見えないこと、ロール不足の「権限なし」、フォームの候補から他の申請の領収書が除かれることが `npm run test` で通る

- [ ] 2.6 申請の作成・修正・下書きの削除の判断
  - 作成（作業者ロールでなければ「権限なし」、件名の検証 → 領収書の規則 → 下書き・revision 1・承認者なしで申請と紐付けと作成の履歴を挿入）を作る
  - 修正と削除を、1 つのトランザクションの中で「申請を読む → 遷移規則の判断 → 入力と領収書の規則 → 反映（revision を 1 増やし更新日時を記録）」の共通の手順で作る。領収書の規則は、入力の領収書 ID（未検証の文字列）をブランド型にキャストせずにそのまま領収書の参照に渡し、存在しない・他人の・他の申請に含まれる領収書があれば項目エラーとし、所有者の確認は本 spec で行う。紐付けに書く ID は参照で返された領収書の ID だけを使う
  - 拒否した場合は DB を変更しない。ロックの付け外しは行わない
  - 結合テスト（領収書は 2.4 と同じフィクスチャで用意する）で、作成で下書きになり領収書がロックされないこと、他人・存在しない・他の申請の領収書を含めると項目エラーで DB が変わらないこと、修正で外した領収書が別の申請の候補に戻ること、古い revision での修正・削除が「状態が変わった」になること、差し戻しの申請の削除と申請中・精算完了の申請の修正・削除が拒否されることが `npm run test` で通る
  - _Requirements: 1.2, 1.3, 2.1, 2.2, 2.4, 3.1, 3.2, 3.3, 3.5, 3.6, 3.7, 6.4, 7.4, 7.5_

- [ ] 2.7 提出・再提出・承認・差し戻しの判断とロックの付け外し
  - 提出・再提出（承認者候補がいなければ「提出できる承認者がいません」、承認者の未指定・候補外を項目エラー、領収書 0 件を項目エラー、申請中にして承認者と提出日時を記録、承認者付きの提出または再提出の履歴、申請の全領収書をロック）を 2.6 の共通の手順で作る
  - 承認（精算完了にし承認の履歴、ロックは変えない）と差し戻し（コメントを検証し、差し戻しにしてコメント付きの履歴、申請の全領収書のロックを解除）を作る
  - ロック・解除に渡す領収書 ID は、利用者の入力ではなく申請の紐付けから読んだ ID を使う
  - 状態の変更・承認者の記録・履歴・ロックの付け外しは、すべて同じトランザクションの中で行い、途中の例外で全体が巻き戻るようにする
  - 結合テスト（領収書は 2.4 と同じフィクスチャで用意する）で、作成 → 提出（2 件ロック）→ 差し戻し（ロック解除、コメント記録）→ 1 件外して再提出（外した領収書はロックなし）→ 承認（ロック維持）の一連の流れの各段階の状態・履歴・ロック、自分自身・作業者だけのユーザー・存在しないユーザーの指定の拒否、同じ revision での承認の後の差し戻しが「状態が変わった」になること、申請者による承認と指定外の承認者による差し戻しが「見つからない」になること、ロックの付与・解除が例外を投げたとき（下流向けの公開面のロックの関数だけをテストで差し替え）状態・revision・履歴が元のままであることが `npm run test` で通る
  - _Requirements: 4.2, 4.3, 4.5, 4.6, 4.7, 5.1, 5.2, 5.4, 5.6, 5.8, 6.3, 6.4, 6.5, 6.6, 7.1, 7.2, 7.3, 10.2_

  - 承認者の選択（ラベル付き、先頭に「選択してください」、直前の承認者を初期選択）と「提出する」または「再提出する」のボタンを、提出か再提出かの区別に従って出す。候補が 0 件なら「提出できる承認者がいません」だけを出す。承認者・領収書の項目エラーを選択欄に関連付けて表示する
  - 下書きの削除の確認領域（削除ボタン → 確認の見出しにフォーカス → 「削除する」「キャンセル」、キャンセルで元のボタンにフォーカスを戻す、成功で一覧へ）を作る
  - 描画テストで、候補 0 件で提出ボタンがないこと、初期選択、ボタン名の切替、初期表示に削除の確認領域がないことが `npm run test` で通る
  - _Requirements: 3.3, 3.4, 4.1, 4.4, 4.5, 4.6, 4.7, 12.2, 12.3, 12.4_

- [ ] 3.6 承認と差し戻しの操作領域
  - 「承認する」→ 確認領域（精算完了となり以後変更できない旨）→「承認を確定する」「キャンセル」の承認の操作と、ラベル付きの任意のコメント欄と「差し戻す」ボタンの差し戻しの操作を、別々の操作として作る。コメントの項目エラーを関連付けて表示し、入力を保持する。どちらかの送信中は両方のボタンを無効にする
  - 描画テストで、承認と差し戻しが別のボタンであること、初期表示に承認の確認領域がないこと、コメント欄のラベルが `npm run test` で通る
  - _Requirements: 5.1, 5.2, 5.4, 12.2, 12.3, 12.4, 12.6_

- [ ] 4. 画面の組み立て
- [ ] 4.1 作業者の申請一覧と作成の画面
  - 一覧画面はローダーで作業者の申請一覧を読み、「権限なし」なら作業者ロールが必要な旨だけを表示し、それ以外は見出し・作成画面へのリンク・一覧を表示する
  - 作成画面はローダーでフォームのデータを読み、「権限なし」なら作業者ロールが必要な旨、それ以外は見出しと作成のフォームを表示する
  - 開発サーバーで、作業者が作成画面から領収書を選んで下書きを作ると詳細画面に遷移し、一覧に「下書き」として表示される。承認者のみのユーザーでは両画面に作業者ロールが必要な旨が出る
  - _Requirements: 1.1, 1.2, 8.1, 8.4, 8.5, 11.5_

- [ ] 4.2 申請の詳細画面
  - ローダーで詳細を読み、「見つからない」なら申請が見つからない表示にする。詳細と操作履歴を表示し、許される操作の一覧に従って、修正画面へのリンク・提出・下書きの削除・承認と差し戻しの操作領域だけを置く。画面では状態の比較を書かない
  - 成功した操作の後に最新の状態・内容・履歴が表示される
  - 開発サーバーで、下書きでは修正・提出・削除だけ、指定承認者が開いた申請中では承認・差し戻しだけ、精算完了ではどの操作も表示されない
  - _Requirements: 3.6, 5.8, 10.1, 10.4, 10.5, 11.4_

- [ ] 4.3 申請の修正画面
  - ローダーで修正用のフォームのデータを読み、「見つからない」なら申請が見つからない表示、「権限なし」なら作業者ロールが必要な旨、「修正できない」なら詳細へのリンク付きの通知、それ以外は見出しと修正のフォームを表示する
  - 開発サーバーで、差し戻しの申請の件名と領収書を変えて保存すると詳細に反映され、申請中の申請の修正画面の URL を直接開くと修正できない旨が出る
  - _Requirements: 3.1, 3.6, 11.4, 11.5_

- [ ] 4.4 承認者の申請一覧の画面
  - ローダーで承認者の申請一覧を読み、「権限なし」なら承認者ロールが必要な旨だけを表示し、それ以外は見出しと一覧を表示する
  - 開発サーバーで、指定された承認者の一覧に提出済みの申請が表示され、作業者のみのユーザーでは承認者ロールが必要な旨が出る
  - _Requirements: 9.1, 9.5, 11.5_

- [ ] 4.5 トップ画面からの導線
  - 作業者ロールなら「自分の申請」、承認者ロールなら「自分宛ての申請」へのリンクを表示する
  - 既存の領収書の導線と 2 つの申請の導線を、ラベル付きの 1 つのナビゲーション領域の中のリストにまとめる。領収書の導線の文言・リンク先・表示条件は変えず置き場所だけを移し、導線以外の既存の表示は変えない（共有ファイルへの変更のうち、追記でないのはこの組み直しだけ）
  - 開発サーバーで、作業者のみ・承認者のみ・両方のロールのユーザーにそれぞれ該当するリンクだけが、領収書の導線と同じナビゲーション領域のリストの項目として表示される
  - _Requirements: 12.1_
