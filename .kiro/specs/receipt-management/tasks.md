- [x] 1.1 領収書の型・費目・作業者ロールの判定

- [x] 1.2 領収書とロックの記録のテーブル定義とマイグレーション
  - 領収書（所有者はユーザーへの外部キー、日付は文字列、金額は 1〜9,999,999 の CHECK 制約、費目は 7 値の CHECK 制約、メモは既定値が空文字、作成・更新日時）と、ロックの記録（領収書 ID を主キーとし、領収書を削除制限付きで参照）を design の Physical Data Model どおりに定義する

  - `npm run db:generate -- --name receipts` で生成した SQL マイグレーションとメタ情報をコミット対象に加える

  - _Requirements: 1.4, 2.4, 2.6, 7.1, 7.6_

- [x] 1.3 領収書モジュールの import 境界
  - 領収書モジュールの内部ファイルをモジュールの外から import できないようにする制限パターンを定義し、機能モジュールの境界の一覧に追加する。外から使えるのは公開面・外部キー参照用のテーブル定義・画面部品・下流のサーバーコード向けの公開面の 4 つと、テストファイル専用のフィクスチャ（`@/receipts/test-fixtures.server`）だけにする
  - フィクスチャは内部の制限から除外したうえで、identity のシードと同じくテストファイル専用の制限（`testOnly`）をかけ、モジュールの外ではテストファイルからだけ import できるようにする
  - steering の構造ドキュメントの import 境界の節に、領収書モジュールの公開面（テストファイル専用のフィクスチャを含む）を 1 行追記する
  - 一時ファイルで試し、ルートのファイルからサービスや画面部品の内部ファイルを import すると Lint エラーになり、4 つの公開面は検出されないこと、フィクスチャはテストファイル以外からの import が検出されモジュールの外のテストファイルからは検出されないことを確かめてから一時ファイルを削除する。`npm run lint` がエラーなしで終わる
  - _Requirements: 7.5_

- [x] 2. コア：検証、永続化、操作の判断、公開面
- [x] 2.1 (P) 入力の形と項目の検証
  - Server Function の入力の形（5 項目がすべて文字列か、領収書 ID が空でない文字列か、更新は ID と 5 項目の組か）を確かめ、不正なら Error を投げる検証を作る
  - 項目の規則（日付の必須と実在、金額の必須・半角数字の整数・1〜9,999,999、支払先の必須と 100 文字、費目の定義済み、メモの 500 文字と任意）を design の表どおりのメッセージで判定し、支払先とメモの前後の空白を除いた検証済みの項目を返す。誤りのある項目はすべて返す

- [x] 2.2 (P) 領収書とロックの記録の読み書き
  - 所有者ごとの一覧（日付の降順、同じ日付なら作成の新しい順、さらに ID の降順）、ID での 1 件取得、複数 ID での取得（未検証の文字列を受け、引数の順、存在しない ID・形式が不正な ID は除き、重複は 1 件にまとめる）を、ロック中かどうかを付けて返す
  - 新しい ID と作成・更新日時を付けた挿入、所有者を変えない更新、削除、ロックの付与（既にロック中なら変えない、存在しない ID は外部キー違反（`SQLITE_CONSTRAINT_FOREIGNKEY`）で失敗）とロックの解除（ロックされていない ID は無視）を作る。書き込みは自分でトランザクションを開始しない
  - 結合テスト（in-memory DB とシードユーザー）で、一覧の並び順、ロックの有無による表示、更新で所有者が変わらないこと、ロック中の領収書の行を直接削除すると外部キー（RESTRICT）違反（`SQLITE_CONSTRAINT_TRIGGER`。`SQLITE_CONSTRAINT_FOREIGNKEY` ではない）になること、範囲外の金額と未定義の費目が CHECK 制約で拒否されること、ファイル DB を閉じて開き直しても登録内容が読めることが `npm run test` で通る
  - _Boundary: ReceiptRepository_
  - _Requirements: 1.2, 1.4, 3.1, 3.2, 3.5, 4.4, 5.2, 7.1, 7.4_

- [x] 2.3 現在ユーザーによる操作の判断
  - 一覧・1 件取得・登録・更新・削除のそれぞれで、ロール → 存在と所有者 → ロック → 項目の検証の順に判定する。作業者でなければ DB に触れずに「権限なし」、存在しないか他人の領収書なら区別せず「見つからない」、ロック中なら入力の誤りより先に「ロック中」を返す
  - 存在・所有者・ロックの確認と書き込みを 1 つのトランザクションで行い、拒否した場合は DB を変更しない。登録と更新に同じ項目の検証を使う
  - DB の障害は握りつぶさずに伝播させる
  - 結合テストで design の Testing Strategy の ReceiptService の項目（所有者ごとの分離、承認者のみのユーザーの全操作の拒否、両ロールのユーザーの許可、他人と存在しない ID が同じ結果、不正入力で DB が変わらないこと、更新・削除の成功、ロック中の拒否、取得後のロックによる拒否、ロック解除後の成功、初期状態でロックなし、閉じた DB での例外の伝播）が `npm run test` で通る
  - _Depends: 2.1, 2.2_
  - _Requirements: 1.2, 1.3, 2.10, 3.1, 3.6, 4.2, 4.3, 4.4, 5.2, 6.1, 6.3, 6.4, 6.6, 7.1, 7.3, 7.4, 7.6, 8.5_

- [x] 2.4 (P) 下流のサーバーコード向けの参照とロックの付け外し
  - 複数 ID での領収書の参照（未検証の文字列の配列を受け、存在しない・形式が不正な ID は Error なしに結果から除く）、所有者ごとの一覧（画面と同じ順序）、ロックの付与と解除（検証済みの領収書 ID の配列を受ける）を、下流向けのサーバー専用の公開面として design の ReceiptsDownstreamApi のシグネチャどおりに提供する。権限の確認はせず、付け外しは自分のトランザクション（呼び出し側のトランザクションの中では入れ子）で行う
  - 付与と解除はどちらも冪等にし、存在しない ID を含む付与は Error を投げて何もロックしない
  - 2.3 と並行して進められる。2.2 の読み書きの関数に委ねるため、2.2 の完了が前提
  - 契約テストで、付与・解除を 2 回呼んでもエラーにならないこと、存在しない ID を含む付与で他の ID もロックされないこと、外側のトランザクションをロールバックするとロックも残らないこと、参照の順序と、存在しない ID・空文字・UUID でない文字列の除外と重複のまとめが `npm run test` で通る

## Implementation Notes
- ON DELETE RESTRICT の違反（ロック中の領収書の行の削除）は better-sqlite3 では `SQLITE_CONSTRAINT_TRIGGER`（メッセージは "FOREIGN KEY constraint failed"）になる。挿入側の外部キー違反は `SQLITE_CONSTRAINT_FOREIGNKEY`。2.2・2.6 のテストとエラーの扱いはこれを前提にする
- マイグレーションを追加すると適用件数が変わる。`src/db/client.test.ts` は journal のエントリ数と比べる形にしてあるので、以降のマイグレーション追加では直さなくてよい
- 読み書きの関数は `AppDatabase` を受ける。`db.transaction(...)` の中でも同じ `db` を渡せばそのトランザクションに含まれ（better-sqlite3 は 1 接続で、入れ子は SAVEPOINT になる）、drizzle の `tx` を渡す必要はない。`updateReceiptRow` は存在しない ID で Error を投げ、`deleteReceiptRow` は存在しない ID では何もしないので、呼び出し側が先に存在を確かめる
- インストール済みの `useServerFn` はリダイレクト（現在ユーザー未選択）を捕まえて遷移し、結果として `undefined` を返す。画面部品の送信処理は `undefined` を例外扱いせずに終える（`receipt-form.tsx` の guard を参照）
- フォームの `locked` の警告はフォームの状態に持つため、`router.invalidate()` で編集画面が読み取り専用に切り替わると消える。4.2 では `LockedNotice` が同じことを伝えるかを確かめる
- 画面部品のテスト環境は node の `renderToString` のみで、クリック・フォーカス移動・送信結果ごとの処理は自動テストで確かめていない（結果の振り分けは純粋関数 `toReceiptFormOutcome` / `toDeleteReceiptOutcome` で単体テスト済み）。5.1 の E2E で、フォームの誤り時のフォーカス、削除の確認領域の「開く → 見出しにフォーカス → キャンセル → 元のボタンにフォーカス」を必ず確かめる
